# A card's CI

The CI page shows, for one card, whether its work builds (c-642, c-639): the checks on its
pull requests, and the CI server's builds that carry its work, with each build's stages and
the end of a failed step's log. It is a page of the card, beside its plan and outcome, and
each links to the others.

Code: `keel/ciroute.py` (the route and its data), `app/ui.ci.js` (the page), and in a pack
the `ci` verb (the work pack's `<install>/packs/work/ci`, `cisight.py`, `ciserver.py`).

## What a CI server builds, and so what the page matches

The work pack's server builds only the shared branches. Probed read only
(2026-10-04) with the user's token:
- Each repo is a multibranch pipeline, `<repo>-pipeline`.
- Each has three branch jobs, one per shared branch. No card branch and no pull request is
  built there.
- A build lists its commits (`changeSets`: sha and message, and the message carries the story
  ref), its stages (`wfapi/describe`) and, for a failed stage, its steps. Each step has its
  log, whose last 10 KB the server keeps as `wfapi/log`, where a test run's summary is.
- There is no test report.

So a card's CI has two halves:
1. **Its pull requests' checks:** the code host's commit statuses on each head.
2. **The shared-branch builds that carry its work.** A build matches when its commits include
   one of the card's pull requests' commits, or when a commit message names the card's
   story. A cherry-pick (c-641's early merge) has a new sha but keeps the ref.

The commits are read from the code host, not the worktree, so a card whose worktree was
reaped reads the same.

## The capability and the verb

`ci` is a pack capability (`packs.NEEDS`: it needs a `ci` verb at the pack's root), with a
readiness row per space (`readiness.CAPABILITIES`: "CI builds", step `integrations`) and a
row on the Start page. Core never names the server: the pack's `[terms]` may give `ci_name`
(core's default is "the CI server").

`ci <id>` prints JSON and writes nothing:

```
{"card", "story",
 "checks": [{"repo", "pr", "url", "head", "statuses": [{"name", "state", "url", "updated"}]}],
 "builds": [{"repo", "branch", "number", "url", "result", "building", "started", "duration",
             "matched": {"commits", "ref"}, "stages": [{"id", "name", "status", "ms"}],
             "failed_stage", "log": [lines]}],
 "notes": [what it could not read]}
```

- **Builds, newest first.** The newest 30 of each branch job are read. Stages are read for
  the newest 6 matched per branch. The failed step's last 80 lines are read for the newest 2
  failed builds; an older failure carries `log_note`, which says so.
- **Time:** each call to either service waits at most 15 s, and the whole read, every code
  host call and each page of its listings included, stops at 55 s (`ciserver.BUDGET`,
  `ciserver.left`; the code host's `codehost.DEADLINE`, set for the read), under the deck's
  90 s. The first call the CI server does not answer, missing credentials, or a refused
  token (401, 403) marks it gone for the read (`ciserver.Unreachable`): every later call is
  refused at once, and the notes say it once. A code host failure that is not an HTTP status
  (no answer, no credentials, out of time) stops the pull request reads the same way
  (`cisight.host_gone`); a repo with no known slug is about that repo alone. Credentials are read once a read.
- **What it cannot read is a note, never an error:** a repo with no pipeline, the server
  unreachable, no pull request yet, or a commit listing refused (then builds are matched by
  the story alone). So the page always draws what it has.
- **The work pack's credentials** are the CI server's MCP entry in `~/.claude.json`, the same
  file and pattern as the code host's. They are the `CI token` requirement, `for = ["ci"]`.

## The page

- **`/ci/<id>`** is served by the plan page's shell (`PLAN_PAGE` takes `ci`; `app/plan.html`
  loads `ui.ci.js`, and `viewPlan` hands it the body).
- **The header** has the viewer's tabs, every other page of the card (`K.docTabs`, from the payload's
  `docs`). The plan and outcome headers list `ci` too when the card has a repo and its
  space's `ci` readiness row is ready (`ciroute.offered`), the row the pane's CI button
  reads, so the link and the button agree. The page, opened anyway, still runs the verb and
  says its own words. So plan, outcome and CI switch to each other, the
  shape c-644 finishes.
- **`/api/ci/<id>`** (`ciroute.payload`) runs the pack's verb with a 90 s budget and answers
  `{card, docs, at, ci, why}`. `why` is the readiness sentence (or the failure) when there is
  nothing to show.
- **It is read when the page opens and on Refresh,** never polled, never on a board event
  (the shell's `K.loadPlan` skips `ci`), and never kept: an external read when the user looks, so
  nothing has to agree with it. One read runs at a time. A failed Refresh keeps what was
  read, the header and Refresh, and says it failed; a failed first read still draws the
  header and Refresh. The page wears its card's space palette (`K.wearSpace`, the plan
  shell's).
- **The page draws:**
  - a summary line, each check state counted apart (failed, running, passed, others);
  - the pull requests' checks, one row per status;
  - the builds, each with its result chip, age and duration, why it matched, its stages as
    chips, and a failed step's log in a scrolling block;
  - the notes.

  It is phone first, in the plan page's tokens.
- **The card pane** draws **CI** (`open-ci`, in the Pages group) from building on, on a card
  with a repo whose space has `ci` ready (`K.putCi`, at shipping too). It opens beside the
  deck as the plan does.
