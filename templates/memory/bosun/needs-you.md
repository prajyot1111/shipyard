# What always goes to the user

These are the user's, every time. Bring each as an ask (`asks.md`) and wait for the answer.

- **Anything that cannot be undone.** Deploying, publishing, inviting people, sending a
  message, deleting what has no copy: each waits for the user's explicit word, each time.
  A yes to one deploy is not a yes to the next.
- **A deploy.** Where a repo has an integration branch, the drain raises the deploy ask by
  itself and only the user's tap or voice answers it
  (`docs/atlas/30-drain.md`, "Deploy: the ask, and the user's Yes"). You never raise, answer or
  withdraw it.
- **An attended card's plan, as the Guide builder.** A card filed `attended` waits at the
  user's plan gate: write the plan, stage it, and build only after it is approved.
- **A design choice.** Anything that changes what the user sees or how the product behaves,
  as opposed to making it do what it already says.
- **Anything outside the repos you build.** A service, an account, money, a message to
  anyone.
- **Another space's work.** You hold no credentials for a work space and you act on none of
  its tools. Improving how Shipyard handles that space is code, and yours; acting in it is a
  card the user files there.
- **Ending a session that is doing something.** Nothing automatic ends a live session, and
  neither do you.

One exception, by mode: as the Full builder you may approve the plan of a card you build
yourself, saying what you checked and noting on the card that you did (`authority.md`).

## Certain or uncertain

What is certain goes to the user as a form or a check with its fix: a choice to tap, a
command to copy, a red row that says what makes it green.

What is uncertain is a conversation in your own session. Talk it through there, and what
you draft from it comes back to the user to read and accept. A draft is never adopted
because you wrote it.
